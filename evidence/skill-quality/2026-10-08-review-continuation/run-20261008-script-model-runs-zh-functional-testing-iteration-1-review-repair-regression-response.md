### 1. 任务理解

范围是按给定业务契约比较三份静态 fixture：成功支付要求订单为 `PAID`，且该订单恰有一笔 ledger credit。只依据用户提供的契约和 fixture；没有真实执行测试。

当前假设：fixture 中的订单状态和 ledger 数量，是用于比较的业务结果。toast 不属于契约规定的成功条件。

### 2. 风险和优先级

- **高：ledger 重复入账。** 同一订单多出一笔 credit，直接违反唯一入账要求。
- **高：订单状态未完成。** UI 显示成功但订单仍为 `PENDING`，会造成用户看到的结果与业务状态不一致。
- **一般：toast 断言缺失。** 契约未要求 toast，因此单凭缺少 toast 断言不构成业务后置条件失败。

### 3. 核心功能覆盖

核心覆盖是支付成功后的两个业务后置条件：订单状态为 `PAID`，并且该订单恰有一笔 ledger credit。成功提示属于 UI 表现；除非另有需求把它纳入契约，否则不影响本次业务判定。

### 4. 关键场景清单

- 正向场景：支付成功后同时满足订单状态和唯一入账条件。
- 异常场景：界面提示成功，但持久化业务状态未达到契约要求。
- 边界场景：重复处理同一支付回调后，ledger credit 数量仍保持为一笔。
- 角色、权限和其他集成路径不在给定材料中，无法据此判断覆盖情况。

### 5. 执行备注

**最小验证建议（未执行）：** 对一个成功支付订单检查其持久化状态为 `PAID`，并核对该订单的 ledger credit 数量恰为 1；随后重放同一回调，再核对数量仍为 1。检查应针对同一订单，并在支付处理完成后读取结果。toast 可另作 UI 检查，但不是本契约的判定条件。

以下 `PASS` / `FAIL` 仅表示 fixture 材料与契约的比较结果，不代表真实测试执行。证据来源仅为用户提供的契约文本和各 fixture 描述。
