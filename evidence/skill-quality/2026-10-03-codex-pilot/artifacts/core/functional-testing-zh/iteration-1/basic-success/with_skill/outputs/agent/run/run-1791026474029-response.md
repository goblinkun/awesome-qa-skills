**1. 任务理解**

为电商「下单→支付→发货」制定 SIT 功能测试方案初版，重点验证支付回调超时是否引发状态不一致、重复处理或错误发货。本方案未执行测试。

- **已确认事实：**即将发版；环境为 SIT；角色包括买家、卖家运营、仓配；支付回调偶发超时。
- **当前假设：**支付结果由支付渠道确认；前端支付成功提示不能单独作为发货依据；同一支付结果重复通知应只产生一次业务效果；未确认付款的订单不得进入发货流程。上述规则需与需求核对。
- **范围：**订单创建、支付结果处理、订单与支付状态一致性、履约触发、发货及角色权限。
- **暂不纳入：**完整退款退货流程、营销组合、压测。取消与付款冲突涉及的退款处置仍需验证。

**2. 风险和优先级**

| 优先级 | 风险 | 业务影响 |
|---|---|---|
| P0 | 渠道已收款，订单未更新或无法恢复 | 买家付款后无法履约 |
| P0 | 回调超时重试导致重复处理 | 重复扣库存、重复创建履约任务或重复发货 |
| P0 | 未付款、支付失败或错误回调触发发货 | 货损及资金损失 |
| P0 | 支付与取消、关单并发 | 已付款订单被关闭，或关闭后错误发货 |
| P1 | 仓配接收失败、发货反馈延迟或重复 | 漏发、重复发货、状态不一致 |
| P1 | 越权操作或不同角色看到矛盾状态 | 非法履约、售后误判 |

P0 优先执行，并作为建议的发版门槛；P1 随后覆盖。

**3. 核心功能覆盖**

| 流程 | 重点检查 | 数据条件与集成点 |
|---|---|---|
| 下单 | 正常生成订单；库存不足时拒绝；重复提交不会造成非预期订单或库存占用 | 有货、无货、最后一件商品；订单与库存模块 |
| 支付 | 成功、失败、取消支付；回调迟到、重复、乱序及超时恢复 | 待支付、已支付、已取消订单；支付渠道与订单模块 |
| 履约 | 仅符合付款条件的订单进入履约；触发失败可恢复且不重复 | 支付已确认、支付结果未确认订单；订单与仓配 |
| 发货 | 重复操作、失败重试、反馈延迟后状态一致 | 待发货、已发货订单；仓配与物流反馈（如有） |
| 角色权限 | 买家仅访问本人订单；运营按授权处理订单；仓配仅操作授权履约任务 | 两个买家账号及不同业务归属的订单 |

库存占用和扣减时点、运营与仓配具体权限均以已确认需求为准。

**4. 关键场景清单**

执行每条用例时，记录订单标识、支付关联标识、时间线，并核对渠道结果、订单状态、库存变化及履约记录。

| 编号 / 优先级 | 前置条件与操作 | 预期结果 |
|---|---|---|
| F01 / P0 正常闭环 | 买家对有货商品下单并支付成功，运营与仓配按权限完成发货 | 金额正确；付款状态一致；产生一次有效履约与发货结果；各角色看到一致状态 |
| F02 / P0 超时发生在处理前 | 渠道确认支付成功，通过 SIT 故障注入使回调未被业务处理；解除故障后触发约定的重试或补偿 | 最终恢复为正确付款状态；恢复前不得错误发货；恢复后仅履约一次，无重复业务扣款 |
| F03 / P0 已处理但响应超时 | 回调业务处理已成功，使响应延迟或丢失，再重放相同通知 | 重试被幂等处理；付款、库存、履约任务均不重复。这与 F02 分开验证 |
| F04 / P0 重复及乱序通知 | 对同一笔支付串行、并发发送重复成功通知；对已成功支付投递较早的处理中或失败通知（渠道支持时） | 只产生一次有效业务处理；成功状态不被旧通知回退 |
| F05 / P0 支付失败与结果未知 | 分别模拟明确支付失败、买家取消支付，以及支付请求超时但渠道结果未知；尝试继续付款或发货 | 明确失败不进入已支付状态；未知结果按约定查询或恢复，不直接判失败；重复尝试不造成非预期多次收款；不提前发货 |
| F06 / P0 付款与关单竞争 | 在取消或自动关单边界之前、同时、之后完成渠道付款，延迟成功回调到达 | 按确认的冲突规则形成唯一结果；不得丢失已收款事实；应履约或进入明确退款处置，不能长期悬置 |
| F07 / P0 错误或非法回调 | 使用金额不匹配、订单关联错误、校验失败的通知；对未确认付款订单尝试发货 | 非法通知不改变业务状态、不触发履约；错误有可追踪记录；未付款发货被拦截 |
| F08 / P0 库存边界与重复下单 | 两个买家竞争最后一件商品；重复提交下单，再完成成功订单付款 | 不超卖；订单与库存占用一致；失败或关闭订单按规则释放占用；有效订单可以履约 |
| F09 / P1 履约交接失败 | 支付成功后模拟仓配接收超时或失败，再执行允许的重试或补偿 | 已付款事实保留；交接可恢复；只产生一份有效履约任务，失败可定位 |
| F10 / P1 发货重试与反馈异常 | 对待发货订单重复提交发货，模拟反馈延迟、重复到达 | 不重复发货；反馈恢复后状态一致；单号、包裹等信息按需求正确关联 |
| F11 / P1 角色与越权 | 买家访问他人订单；运营处理未授权订单；仓配操作未授权任务；用正常入口及直接请求验证 | 越权被服务端拒绝；合法操作可完成；拒绝操作不改变订单、付款或发货状态 |

回调等待、重试耗尽和恢复时限均需覆盖**约定阈值前、阈值点、阈值后**；具体时间值待补齐，不预设。

**5. 执行备注**

- **准备：**SIT 测试账号、可控制结果的支付测试渠道或替身、独立测试商品与库存、可重置订单、回调重放及故障注入能力。需能区分“未处理就超时”和“已处理但响应超时”。
- **顺序：**先跑正常闭环建立基线，再执行支付超时、幂等、关单竞争等 P0，最后验证仓配恢复和权限。
- **判定：**不能仅看页面提示；应通过获准的查询入口或日志核对资金结果、订单状态、库存及履约记录。以确认的恢复时限判断是否收敛。
- **留证：**保存故障注入位置、通知次数、渠道与业务处理时间、最终状态和履约数量，便于复现偶发问题。
- **建议准出：**P0 全部通过；无未解决的资金不一致、错误发货、重复履约及超卖问题；异常恢复机制已验证。P1 未通过项明确业务影响及发版处置。

**6. 待确认问题**

以下信息缺口直接影响执行和验收：

1. **超时位置与根因线索：**发生在渠道请求、网关、业务处理还是响应返回？是否存在“业务成功但渠道认为失败”的记录？
2. **恢复机制：**渠道如何重试、持续多久？是否有主动查单、对账补偿或人工恢复？允许的最大恢复时限是多少？
3. **状态与冲突规则：**支付成功的判定依据、重复支付处理方式，以及取消／关单后收到成功回调的履约或退款规则。
4. **库存与履约规则：**何时占用、扣减和释放库存？哪个状态允许发货？履约失败如何重试及防重？
5. **角色权限：**运营和仓配各自能查看、修改哪些订单或任务？是否允许人工确认付款或强制发货？
6. **SIT 可测条件：**支付渠道及仓配是否真实接通？能否注入故障、重放通知、查看关联日志？发版具体变更范围及相关历史缺陷是什么？

补齐前可执行正常路径及已具备条件的异常用例；依赖未定义业务规则的场景应标记为“预期结果待确认”，不能直接判通过。
