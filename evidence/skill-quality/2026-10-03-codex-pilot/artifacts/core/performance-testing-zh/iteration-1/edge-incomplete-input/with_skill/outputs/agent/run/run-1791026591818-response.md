### 1. 任务理解

**这是初版探索方案，目标是找到积分兑换的性能拐点，并验证高并发下账务和库存是否正确。当前不能据此判定“满足上线 SLA”。**

- **已确认：**系统为积分兑换；没有 SLA、历史流量。
- **当前假设：**存在积分查询、兑换提交、结果查询；兑换涉及扣积分及库存或权益发放。需核实实际流程。
- **以下所有负载、时长和性能阈值均为初版假设，待产品与研发评审，不代表真实需求或承诺。**

### 2. 性能风险和优先级

| 优先级 | 风险 | 重点验证 |
|---|---|---|
| P0 | 并发兑换造成重复扣分、重复发放、超卖 | 同一用户并发、同一兑换请求重试、多人抢同一商品 |
| P0 | 超时或部分失败导致交易状态不一致 | 客户端超时后的查询和重试；核对积分、兑换记录与发放结果 |
| P1 | 热门商品、库存竞争或账户写入形成瓶颈 | 热点与分散请求对比，观察锁等待、吞吐和尾延迟 |
| P1 | 瞬时流量耗尽线程、连接或下游配额 | 排队、限流、超时，以及降载后的恢复 |
| P2 | 长时间运行出现资源泄漏、积压 | 内存、连接、队列和延迟是否持续增长 |

以上是待验证的风险，不能直接当作已确认根因。

### 3. 建议测试类型

按“基线 → 阶梯负载 → 压力与容量探索 → 突增 → 稳定性”执行；每阶段通过交易正确性检查后，再进入下一阶段。

- **基线：**确认脚本、数据和监控可靠，测低负载耗时。
- **负载：**观察假设负载下的响应和资源消耗。
- **压力与容量：**找到性能拐点及首先饱和的资源。
- **突增：**验证热点抢兑、限流和恢复。
- **稳定性：**检查持续运行后的资源增长及交易积压。

### 4. 场景方案

| 场景 | 执行方式与初版数字假设 | 检查重点 |
|---|---|---|
| 基线 | 单用户完整兑换；随后以 **1 次兑换/秒运行 10 分钟〔假设〕** | 端到端耗时、扣分和发放结果 |
| 混合负载 | 查询积分、提交兑换、查询结果占 **60%/30%/10%〔假设〕**；总请求到达率 **20 → 50 → 100 请求/秒，每档 15 分钟〔假设〕** | 各交易延迟、成功吞吐、资源变化 |
| 热点与竞争 | 相同负载分别访问分散商品和热门商品；热门商品占兑换请求 **80%〔假设〕** | 热点退化、库存边界；另跑同账户并发 |
| 超时与重试 | 在隔离环境模拟响应延迟或依赖失败；同一业务请求重试及查询 | 是否重复扣分或发放、是否能恢复到一致状态 |
| 压力与容量 | 从已稳定档位开始，每档增加 **25%，保持 10 分钟〔假设〕**，直至退出条件触发 | 首次越过阈值的位置、瓶颈及降载恢复 |
| 突增 | 从稳定档位瞬时升至 **3 倍、保持 2 分钟，降载观察 10 分钟〔假设〕** | 限流有效性、排队、恢复时间 |
| 稳定性 | 在探索得到的稳定容量的 **70% 下运行 4 小时〔假设〕** | 内存增长、连接泄漏、积压及账务一致性 |

以**请求到达率**控制负载，同时记录实际并发数，避免响应变慢后压测端自动降低发压量、掩盖问题。混合场景的总请求量与兑换提交量分别统计。

### 5. 指标和退出标准

**临时性能目标，均为假设：**

- 同步兑换提交：P95 ≤ **1 秒**、P99 ≤ **2 秒**；查询：P95 ≤ **500 毫秒**。
- 技术错误率 ≤ **0.1%**。积分不足、库存不足等预期拒绝单列；限流拒绝也单列，不能混入成功量。
- 稳定阶段实际发压量达到计划量的 **95% 以上**；同时报告成功兑换吞吐，不能用拒绝请求充当处理能力。
- 稳定性测试后段 P95 相较稳定起始窗口增长不超过 **20%**，队列和资源占用没有持续增长趋势。

**正确性验收要求：**不得出现重复扣分、重复发放或超卖；按确认的业务规则核对积分流水、兑换记录、库存和权益。若采用异步发放，提交耗时与最终完成耗时分开测量，一致性期限待补充。

**退出条件：**

- 发现账务或库存错误，立即停止该场景，保留证据。
- 技术错误率超过 **5% 持续 1 分钟〔假设〕**，或超时、积压持续失控，停止升压并降载。
- 达到预设最大负载或环境资源边界后结束，不无限加压。

结果应给出：最后稳定档位、首次失效档位、对应延迟和错误、瓶颈证据及恢复情况。容量结论只适用于本次环境、数据和请求分布；未触及拐点时只能报告已验证的容量下界。

### 6. 执行备注

**环境与数据：**使用隔离测试环境和测试账户；积分、库存及发放依赖可清理或模拟。记录环境与生产的配置差异；模拟依赖的结果只能说明本系统表现。准备余额充足/不足、库存充足/临界/耗尽、重复请求及冷热商品数据，避免数据耗尽使正常负载变成大量拒绝请求。

**监控：**同步采集分交易的吞吐、P50/P95/P99、错误和拒绝原因，以及 CPU、内存、GC、线程与连接池、数据库慢查询和锁等待；存在缓存、队列或外部依赖时采集其指标。检查压测端资源和实际发压量，排除工具瓶颈。

**待补充缺口：**

- 产品目标：典型用户等待时间、超时提示、失败后的预期行为及 SLA。
- 业务规则：重复请求如何识别，扣分、扣库存、发放及补偿的边界。
- 流量模型：日常峰值、活动规模、集中到达程度、热门商品占比、用户重试方式。
- 系统范围：实际交易入口、同步/异步链路、依赖及配额。
- 环境数据：部署规格、数据规模、测试环境差异、可用监控。
- 执行条件：测试窗口、资源上限、负责人及数据恢复方式。

缺口未补齐时，可先完成基线和低档位探索，用实测结果修订假设；不能把这些假设阈值当作正式上线标准。
