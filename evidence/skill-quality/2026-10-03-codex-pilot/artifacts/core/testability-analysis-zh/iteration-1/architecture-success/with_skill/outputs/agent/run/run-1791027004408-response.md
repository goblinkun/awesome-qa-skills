**4. 核心分析与执行项**

组件边界与测试接缝应落到实际接口、配置和调用路径：

| 边界 | 测试 seam 与 substitute strategy | 隔离和证据要求 |
|---|---|---|
| 订单服务 → 消息队列 | 使用真实测试队列和隔离主题；通过订单入口产生消息。直接投递契约消息可单独验证消费者，但不能覆盖订单发布逻辑 | 核对生产者、消费者和重试／死信去向；保留消息内容、发布及消费记录 |
| 消息队列 → 支付适配器 | 在真实消费入口验证解析、确认、重投与恢复；消费者契约尚待提供 | 不能把主题隔离等同于消费组隔离；需检查具体队列机制和配置 |
| 支付适配器 → 支付商 | 若支付客户端或目标地址可替换，使用协议兼容的支付商模拟服务控制响应；沙箱用于补充验证真实契约 | 客户端替换能力尚未证实；需提供接口、配置和替身流量证据 |
| 回调 → 接收组件 | 复用现有回调模拟器；补查重复、延迟、乱序、签名及请求关联控制能力 | 保留实际鉴权和解析路径；模拟器不能默认覆盖支付出站故障 |
| 状态持久化边界 | 存储组件未提供，暂不能确定 seam；建议通过受支持的状态查询和隔离数据验证结果 | 需补订单／支付状态模型、事务边界和查询证据 |

替身测试、真实队列测试和支付商沙箱测试应互补。**一个 mock 或一次模拟回调成功，不能证明整条链路的故障处理正确。**

通用维度采用证据成熟度评级，避免给出无依据的数值评分：

| 维度 | 当前判断 | 最小改进、价值与成本 |
|---|---|---|
| observability 可观察性 | 未证实 | 打通订单、消息、支付请求与回调的关联记录，并提供最终状态查询；便于定位中断点。成本中 |
| controllability 可控制性 | 部分具备：E2、E4 | 补出站响应、回调时序和消费者启停控制；使异常可主动触发。成本中 |
| isolation 隔离 | 部分具备：E4 | 核查主题、消费配置、数据、凭据、回调和商户资源；防止跨运行污染。成本低至中，取决于共享资源 |
| determinism 确定性 | 未证实 | 固定输入、故障脚本和配置；可行时控制时钟，否则采用有界等待与明确完成条件。成本中 |
| 数据准备 | 未证实 | 使用脱敏数据和每次运行唯一标识，提供初始化及清理机制；避免旧消息、旧回调污染。成本低至中 |
| fault injection 故障注入 | 已知缺口：E3 | 在隔离环境以依赖替换或代理注入超时、断连、错误响应；覆盖高风险异常。成本中 |
| environment reproduction 环境复现 | 未证实 | 固定应用、队列、配置、接口契约及部署版本，记录沙箱差异；支持他人复现。成本中 |
| 自动化接口 | 未证实 | 提供受鉴权的测试启动、模拟、结果查询及清理接口；减少人工操作漂移。成本中 |

最小测试钩子优先采用隔离环境中的配置和依赖替换，保留鉴权与数据隔离；不应增加可被生产流量触发的故障后门。

以下场景的期望规则须先绑定支付契约和状态机：

| 场景 | 前置条件与刺激 | 判断标准 | 所需证据 |
|---|---|---|---|
| 正常闭环 | 隔离主题与数据准备完成；创建订单，返回成功响应并发送合法回调 | 消息、请求、回调正确关联，最终状态符合契约 | 全链路关联记录、请求／回调记录、最终状态 |
| 处理成功但响应丢失 | 替身可记录已接受请求；随后断连或超时，观察重试 | 不重复产生扣款副作用；不把未知结果直接判为确定失败；后续收敛规则符合契约 | 替身副作用记录、重试请求、状态变化、查询／对账证据 |
| 重复与乱序 | 固定业务标识；重投消息，重复或乱序发送回调 | 不重复产生业务副作用；非法状态迁移被拒绝或按明确规则处理 | 投递序列、处理次数、状态迁移及拒绝原因 |
| 中断与恢复 | 已明确确认及持久化顺序；在支付处理与消息确认之间中断消费者，再恢复 | 无静默丢失；重放与恢复满足约定，并在规定窗口内收敛 | 中断位置、确认记录、重投记录、最终状态 |
| 并行隔离 | 两组独立测试资源；并发运行，向其中一组注入故障 | 消息、回调、数据和故障不进入另一组 | 两组配置、路由记录及独立状态查询 |

**5. 阻塞条件与剩余风险**

目前阻塞的是“异常链路已验证”的结论，而不是继续设计测试：

- 未明确状态机、幂等和未知支付结果的处理规则，无法建立可靠断言。
- 没有出站故障控制能力，无法稳定验证“已处理但响应丢失”等关键场景。
- 没有端到端隔离证据，不应开展并发故障测试。
- 缺少持久化与关联记录，无法区分请求未到达、支付已成功和本地状态未更新。

测试中如发现串环境、非测试商户被调用或重复扣款副作用，应停止相关运行、保留证据并交由支付负责人处理。替身通过后仍需沙箱契约验证；沙箱无法代表的行为，应列为剩余风险，由业务与架构负责人决定补测或接受。

**6. 下一步与 evidence gaps**

建议按以下顺序补证：

1. **架构／支付负责人**：提供原始架构图、回调路由、支付接口、状态机及重试／幂等规则，确定测试断言。
2. **平台负责人**：提供主题、消费者、重试去向、数据、凭据和回调的隔离配置，执行两组并行隔离验证。
3. **适配器负责人**：证明出站依赖可替换，并实现隔离环境中的最小故障控制，优先验证响应丢失场景。
4. **QA 与平台负责人**：保存版本、配置、输入、故障时序和结果证据，验证正常闭环及重复／乱序场景可重复执行。

完成这些补证前，可以认可“已有部分测试资产”，但不能认可“支付异常链路可测试性已通过”。
