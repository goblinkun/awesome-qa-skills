## 1. 任务理解

**已确认事实：**本次发版涉及电商「下单→支付→发货」流程；测试环境为 SIT；角色包括买家、卖家运营、仓配；已知风险是支付回调偶发超时。

**当前假设：**订单只有在支付结果被系统确认后才可进入发货流程；SIT 能构造支付成功、失败，以及回调延迟、超时和重复的测试条件。以下预期以此为基础，具体状态名称和处理时限以产品规则为准。

## 2. 风险和优先级

- **P0｜资金与订单不一致：**买家已付款但订单长期未确认，或未付款订单被发货。
- **P0｜超时后的重复处理：**回调重试、迟到或并发到达，导致重复记账、重复推进订单或重复发货。
- **P0｜跨角色误操作：**卖家运营、仓配在支付状态不明确时仍能推进发货。
- **P1｜边界状态冲突：**订单取消或超时关闭与支付成功、支付失败几乎同时发生。

## 3. 核心功能覆盖

以同一笔订单贯穿检查：**买家下单并支付 → 支付结果进入订单 → 卖家运营查看并处理 → 仓配发货 → 买家查看最终状态**。每步核对页面状态、订单与支付记录、角色可执行操作及操作记录；支付结果进入订单是重点集成点。

准备至少三类数据：可正常下单的商品、库存不足的商品、用于触发取消或关闭边界的订单。每个支付场景使用可追踪的订单和支付标识，便于核对一次支付是否只产生一次业务推进。

## 4. 关键场景清单

| 优先级 | 场景与执行动作 | 关键预期 |
|---|---|---|
| P0 | **正常闭环：**买家下单并支付成功；卖家运营处理；仓配发货 | 支付、订单、发货状态一致；仅符合条件的订单可发货；三类角色看到各自正确的状态与操作 |
| P0 | **支付成功，回调处理超时：**制造回调超时，再检查订单状态及后续处理 | 超时期间不把结果不明的订单当作已付款发货；最终支付结果得到确认或进入明确的异常处理流程；不存在已收款却被静默遗漏的订单 |
| P0 | **回调超时后重试／重复送达：**对同一支付结果多次回调 | 订单只完成一次支付状态推进；不产生重复发货任务或重复业务记录 |
| P0 | **回调迟到：**先观察超时后的订单，再送达成功回调 | 迟到结果被正确关联到原订单；若订单已取消或关闭，按既定规则处理资金和订单，不能直接发货 |
| P0 | **支付失败或结果仍未知：**买家尝试支付后分别构造失败、未获明确结果 | 卖家运营与仓配均不能将其当作已付款订单发货；买家看到的状态和可重试操作符合规则 |
| P0 | **角色权限：**分别以买家、卖家运营、仓配尝试推进支付确认和发货 | 买家不能代替运营或仓配操作；仓配不能绕过支付确认；越权操作被拒绝且状态不变 |
| P1 | **取消／关闭与支付成功交错：**在状态切换前后分别送达成功回调 | 最终订单与资金处置符合规则，不出现“已关闭却直接发货”或无人处理的已付款订单 |
| P1 | **库存边界：**库存不足时下单；可下单商品支付后检查可发货数量 | 下单、库存占用和发货数量一致；库存不足不会产生可发货订单 |

## 5. 执行备注

优先在 SIT 使用可控的支付模拟或故障注入，分别制造**延迟、超时、重复、迟到**回调；每次记录时间线、订单标识、支付标识和各角色看到的状态。若无法注入，先执行可复现部分，并将回调风险标为未验证。

建议发版门槛：所有 P0 场景通过；不得遗留未付款可发货、已付款无明确处置、重复发货的问题。P1 未通过时应记录具体影响和处置决定。

## 6. 待确认问题

1. “支付回调超时”具体发生在支付方发送回调、系统接收处理，还是系统返回应答阶段？支付方是否重试，重试规则是什么？
2. 回调超时后，系统通过什么机制确认最终支付结果？允许订单保持“结果未知”多久，何时告警或人工处理？
3. 订单取消／关闭与支付成功冲突时，预期是恢复订单、退款，还是进入人工处理？
4. 发货的准确前置条件是什么？卖家运营和仓配各自有哪些操作权限？
5. SIT 是否支持上述故障注入，以及支付、订单、发货记录的交叉核对？
