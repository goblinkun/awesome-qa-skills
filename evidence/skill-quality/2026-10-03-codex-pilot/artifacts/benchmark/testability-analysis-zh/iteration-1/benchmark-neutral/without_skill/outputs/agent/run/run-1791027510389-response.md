这套架构具备两个已知测试入口：消息队列的隔离主题、沙箱的回调模拟器。它们有助于测试消息消费和回调处理，但不足以证明支付链路可重复验证。当前最大的缺口是：无法主动构造支付商故障，且支付结果不确定时的处理机制、异步交付语义和隔离范围尚未明确。

以下是评审与验证方案，**尚未执行；不能据此声称方案有效或架构已通过验证。**

**事实与待核验项应分别记录。**

| 输入明确给出的事实 | 待核验判断及所需证据 |
|---|---|
| 订单服务通过消息队列调用支付适配器 | 发布是否与订单持久化一致；需要发布代码、事务设计及失败记录 |
| 适配器依赖外部支付商 | 超时、重试、查询、幂等和限流契约；需要适配器实现及支付商契约 |
| 沙箱存在回调模拟器 | 是否支持重复、乱序、延迟、合法签名，以及是否经过真实回调入口 |
| 沙箱没有故障注入入口 | 其他层能否注入网络、协议或进程故障；不能直接推断“所有故障均不可测试” |
| 队列可配置隔离主题 | 消费组、重试队列、死信队列及下游资源是否同时隔离 |

不能默认队列“恰好一次”交付、支付商支持幂等、回调可靠送达，或沙箱行为等同真实支付环境。

**先把组件与异步边界变成可检查的测试接缝。**

| 组件或边界 | 建议接缝与控制点 | 重点验证 |
|---|---|---|
| 订单持久化 → 消息发布 | 可替换发布接口；真实数据库与队列的集成测试 | 已保存但未发布、已发布但状态未提交等窗口。若确有跨系统一致性缺口，再评估事务发件箱 |
| 队列 → 适配器消费者 | 保留真实消息解析；允许测试驱动消费、暂停和重投 | 消费确认时机、重复投递、处理后确认前崩溃、重试耗尽、死信 |
| 适配器 → 支付商 | 在支付客户端接口和 HTTP 边界设置接缝 | 请求映射、错误分类、幂等键、超时及“不知道是否已扣款”的结果 |
| 支付商 → 回调入口 | 通过真实入口投递模拟回调；使用测试签名配置 | 验签、重复、乱序、延迟、未知订单、金额或币种不匹配 |
| 支付结果 → 订单状态 | 状态转换接口、持久化查询；若经消息返回，覆盖该队列 | 非法转换、并发更新、旧事件覆盖新状态 |
| 查询或对账补偿 | **是否存在待核验**；若存在，提供单次触发入口 | 无回调、结果不明和长期处理中订单能否收敛 |

异步边界的核心断言应是业务不变量，例如“同一逻辑支付不会产生非预期的重复扣款”“成功状态不会被旧失败事件回退”。具体状态机及退款、取消规则需要业务确认。

**替身应按验证目的分层。**

- **订单组件测试**：使用支付结果替身和可控发布器，快速验证状态转换；它不能证明队列真实交付行为。
- **适配器组件测试**：使用有状态支付商替身，保存幂等键、支付结果和调用记录，支持“已受理但响应丢失”。仅返回固定成功或失败值的 mock 不足以覆盖这个风险。
- **集成测试**：使用真实队列、数据库和可编程 HTTP 替身，验证序列化、确认、重投、持久化与网络行为。
- **沙箱契约测试**：验证真实请求格式、认证、错误映射、回调签名和查询接口。沙箱用于发现替身偏差，其成功不能证明生产环境的容量、故障或结算行为。

替身行为必须注明契约来源和版本；无官方契约或真实记录支持的行为，标记为测试假设。

**隔离、可观察性、可控制性与确定性需要一起设计。**

每次运行分配 `test_run_id`，关联订单号、支付尝试号、幂等键、消息标识和支付商交易号。隔离主题之外，还需核验消费组、重试与死信路径、数据库记录、缓存键、回调路由和沙箱账户。共享账户的余额、限流与回调可能相互影响；无法完全隔离时，应限制并发并明确剩余干扰。

建议输出结构化事件：发布、接收、消费确认、支付请求与响应分类、回调验签结果、状态转换、补偿结果。同时提供只读查询，检查订单状态、支付记录、死信和未完成任务。不要记录凭证、完整敏感支付数据。

测试控制面应能暂停消费、释放指定消息、重投、安排回调、触发一次补偿和配置故障。它应限定在测试环境、需要认证，并防止作用于真实支付端点。

组件测试使用可注入时钟、固定随机种子和事件屏障，避免靠固定 `sleep` 等待。真实队列测试采用有截止时间的条件等待；截止时间由超时及重试配置推导。受控乱序应能重放同一事件序列，但不能把真实异步系统的每次调度都假定为完全一致。

**建议按风险与成本实施，而非先建设完整故障平台。**

| 优先级 | 可执行改进 | 相对成本与依赖 |
|---|---|---|
| P0 | 明确支付状态机、幂等范围、消费确认与重试策略；建立关联标识和查询断言 | 小至中；需要业务和支付集成负责人参与 |
| P0 | 增加支付客户端接缝及最小有状态替身，覆盖受理后响应丢失、重复消息和重复回调 | 中；依赖可拆分的支付客户端 |
| P0 | 建立每次运行的资源隔离、配置清单和安全清理机制 | 小至中；取决于共享资源限制 |
| P1 | 增加 HTTP 故障代理、消费者崩溃点及可控回调顺序；运行真实队列集成测试 | 中至大；涉及测试基础设施 |
| P1 | 若发现一致性或收敛缺口，评估事务发件箱、幂等记录和查询对账机制 | 中至大；涉及存储及业务语义 |
| P2 | 增加长时间延迟、并发竞争、限流和容量验证 | 大；应建立在正确性验证之后 |

成本是相对判断，尚无代码规模、基础设施及团队投入信息，不能给出可靠工期。

故障注入至少覆盖三层：支付替身构造业务错误和结果不明；网络代理构造连接失败、超时、断连和异常响应；进程控制构造处理关键步骤后的崩溃。特别要区分“请求未到达支付商”和“支付商已受理但响应丢失”，后者不能简单按普通失败重试。

**验证时按以下顺序执行并保留证据。**

1. **建立基线与复现包**：固定应用版本、消息模式、队列配置、替身脚本、随机种子及测试数据；记录沙箱配置和契约版本。先跑正常支付与正常回调。
2. **验证重复处理**：重投同一支付消息和同一回调。检查调用记录、支付商侧交易或替身账本、订单状态及幂等记录；仅检查最终订单成功不足以证明没有重复扣款。
3. **验证结果不明**：让替身受理支付后丢弃响应，再投递重试。检查是否沿用正确幂等键，以及查询或对账是否收敛。若支付商不支持相应能力，记录该限制并提交业务决策。
4. **验证乱序与崩溃**：投递重复、迟到和相互冲突的回调；在消费处理后、确认前终止消费者并恢复。检查状态不变量、重投行为及最终收敛。
5. **验证隔离与契约**：并行运行两组测试，检查消息、状态和回调是否串扰；再用沙箱核验替身覆盖的关键契约，记录所有差异。

每个场景需预先写明初始状态、事件顺序、故障位置、期望不变量、截止时间和清理条件。执行产物至少包含版本与配置、事件时间线、相关日志、数据库快照、队列与死信证据、支付请求或交易记录以及判定结果。失败后应能够用这些材料重放，而不是只保存“失败”截图。

目前的证据缺口包括发布一致性、确认时机、幂等实现、回调能力、补偿机制、隔离范围及支付商真实契约。需要人类决定的事项包括：可接受的结果不明持续时间、重试与人工介入阈值、重复扣款风险处置，以及为隔离和故障注入投入多少成本。

即使上述测试通过，仍会残留沙箱与真实支付商差异、共享资源干扰和未覆盖事件组合的风险。当前可交付的是**可实施、可验收的方案**；有效性必须由后续执行记录证明。
