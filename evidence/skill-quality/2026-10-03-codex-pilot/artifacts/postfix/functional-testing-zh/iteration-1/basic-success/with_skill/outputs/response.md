### 1. 任务理解

**已确认事实：**电商「下单→支付→发货」即将发版；测试环境为 SIT；涉及买家、卖家运营、仓配；已知风险是支付回调偶发超时。

测试重点是：**支付结果可靠落单、异常后可以恢复、未付款不会误发货、重复通知不会重复扣减或发货。**本次交付为测试方案，尚未执行测试。

**当前假设：**

- 可以在 SIT 使用测试支付渠道或模拟回调，控制延迟、重复、失败及恢复。
- 订单、支付、库存和发货结果可通过页面、查询工具或日志核对。
- 支付异常存在重试、查单、补偿或人工处理路径；具体机制待确认。
- 下文状态均为业务含义，实际名称和合法转换以需求为准。

### 2. 风险和优先级

| 优先级 | 风险 | 业务影响 |
|---|---|---|
| P0 | 支付成功但订单长期未更新 | 买家已付款，订单无法履约 |
| P0 | 重复、迟到回调及并发处理不一致 | 重复业务处理、误取消、资金与订单不一致 |
| P0 | 未付款或取消订单进入发货流程 | 直接货损 |
| P0 | 库存、订单、发货数据不一致 | 超卖、漏发、重复发货 |
| P1 | 操作失败后无法恢复，角色越权 | 履约阻塞或错误操作扩大影响 |

P0 优先执行；P1 在 P0 主链路稳定后执行，不按模块平均分配测试量。

### 3. 核心功能覆盖

| 流程 | 核心检查 | 角色与集成点 |
|---|---|---|
| 下单 | 商品、数量、金额正确；失败不留下错误订单或库存占用 | 买家；订单与库存 |
| 支付 | 成功、失败、结果未知；回调异常及恢复；资金与订单一致 | 买家、卖家运营；支付渠道与订单 |
| 发货 | 付款资格、发货数量、重复提交、失败恢复 | 卖家运营、仓配；订单与仓储/物流 |
| 全链路 | 各角色看到一致结果；权限有效；异常可追踪 | 三类角色及上述集成点 |

### 4. 关键场景清单

`T` 表示待确认的回调超时阈值；`Δ` 为测试环境可控制的最小时间差。

| 编号 / 优先级 | 前置条件与操作 | 预期结果及核对点 |
|---|---|---|
| 01 / P0 | 买家下单并成功支付；运营处理订单；仓配发货 | 金额、商品和数量全程一致；合法状态依次推进；库存按约定处理；只有一次有效发货 |
| 02 / P0 | 渠道支付成功，但回调在系统处理前超时；随后恢复通知或触发约定恢复机制 | 首次超时期间不能误发货；恢复后准确确认已付款；不要求买家为恢复状态再次支付 |
| 03 / P0 | 回调已完成业务更新，但响应丢失或超时；渠道再次通知 | 重复通知不再次改变资金、库存或履约结果；订单仍可正常发货 |
| 04 / P0 | 同一支付结果连续重复通知、并发通知；再模拟迟到的旧通知 | 同一交易只生效一次；旧通知不使已确认状态倒退；不重复生成履约任务 |
| 05 / P0 | 回调分别延迟至 `T−Δ`、`T`、`T+Δ`；再模拟连续超时后恢复 | 阈值行为符合约定；超时不直接等同支付失败；在约定恢复时限内收敛，超限后可发现并处理 |
| 06 / P0 | 支付确认与买家取消或订单自动关闭几乎同时发生；交换先后顺序 | 按明确的竞态规则得到唯一结果；资金和订单一致；已收款但关闭的订单有处理路径，不能静默遗失 |
| 07 / P0 | 未付款、支付失败、支付结果未知、已取消订单分别尝试发货 | 均不能绕过付款及订单资格校验；页面和实际提交入口均验证；没有库存出库或有效发货记录 |
| 08 / P0 | 库存仅剩 1 件，两个买家同时下单并支付；覆盖一方失败或超时 | 不超卖；付款与可履约结果一致；占用和释放按规则执行，失败订单不永久占库存 |
| 09 / P0 | 发货提交成功但响应超时；仓配再次提交；另测提交失败后重试 | 成功后重试不重复发货；失败可恢复；订单、库存及外部发货结果一致 |
| 10 / P1 | 买家重复点击支付；支付失败后重试；不同尝试的结果先后到达 | 不产生非预期重复扣款；多次支付尝试归属清楚；旧失败结果不覆盖有效成功结果 |
| 11 / P1 | 买家访问其他买家订单；运营操作非授权订单；仓配尝试修改支付结果 | 在实际操作入口拒绝越权；无数据变更；合法角色仍可完成职责内流程 |
| 12 / P1 | 模拟支付结果与订单归属不匹配、金额不匹配，以及依赖短暂不可用 | 不错误确认付款或推进发货；异常可追踪；依赖恢复后按约定重试或处理 |

若系统支持支付结果真实性校验，补充无效或伪造通知用例；实际校验方式待确认。

### 5. 执行备注

- **数据准备：**三类角色账号、两个买家账号、普通库存及仅剩 1 件的商品；准备待付款、已付款、已取消、已发货订单。多商户或仓库隔离适用时补充对应数据。
- **执行顺序：**先验证正常链路，再执行支付超时及重复通知，随后验证取消竞态、库存和发货，最后验证权限与恢复。
- **结果核对：**每例保存订单与支付关联标识、操作时间、注入故障、状态变化、资金结果、库存和发货结果。观察至约定恢复时限，不能只凭一次页面刷新判定通过。
- **建议发版门槛：**所有适用 P0 通过；无未解决的资金不一致、误发货、重复履约、超卖问题；超时恢复路径经过验证。缺少故障注入或结果观测能力时，对应用例标记“未验证”，不能计为通过。
- **范围限制：**聚焦功能正确性；不包含性能容量、完整安全测试、全渠道兼容回归。退款仅覆盖取消竞态引出的资金处理；完整退款流程是否纳入待确认。执行仅限获准的 SIT 测试资源。

### 6. 待确认问题

以下信息需要在正式执行和判定前补齐：

1. **回调超时发生在哪一段？**渠道发送、系统接收、业务更新还是响应返回？已有日志和复现条件是什么？
2. **超时与恢复规则是什么？**超时阈值、重试策略、查单或补偿机制、最终收敛时限、人工处理入口。
3. **业务状态及竞态规则是什么？**付款与取消/关闭同时发生如何裁决？已收款但订单关闭如何处理？何时允许发货？
4. **库存和履约规则是什么？**何时占用、扣减、释放库存？是否支持拆单、部分发货、多仓及多次支付？
5. **本次发布与 SIT 能力是什么？**具体变更范围、支付渠道、角色权限矩阵、故障注入方法、日志与结果查询能力、可用测试数据。
