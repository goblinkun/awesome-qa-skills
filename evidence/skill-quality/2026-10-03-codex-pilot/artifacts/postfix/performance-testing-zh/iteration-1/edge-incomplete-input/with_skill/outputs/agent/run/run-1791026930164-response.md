**1. 任务理解**

已确认：系统是积分兑换；需求只有“测一下性能”；没有 SLA、历史流量。

初版目标：验证兑换在并发下是否正确，建立性能基线，找出瓶颈、容量拐点和过载后的恢复能力。当前不能判断“是否满足线上需求”。

**以下所有流量、比例、时长和性能阈值均为试测假设，不代表真实需求或正式 SLA；执行前需结合环境校准。** 场景涉及的能力也需确认实际实现。

**2. 性能风险和优先级**

| 优先级 | 关键交易／场景 | 主要风险 |
|---|---|---|
| P0 | 提交兑换：积分扣减、库存扣减、兑换记录 | 重复扣积分、超卖、部分成功导致账实不一致 |
| P0 | 同一用户并发兑换、重复提交、超时重试 | 幂等失效、余额竞争、失败后仍扣积分 |
| P0 | 多用户兑换同一热门商品、库存临界 | 热点锁竞争、库存争抢、尾延迟上升 |
| P1 | 查询积分、商品和兑换结果 | 查询拖慢写入，结果延迟或不一致 |
| P1 | 持续兑换、突增后回落 | 连接耗尽、资源泄漏、积压无法消退 |

若存在异步发奖或外部履约，还需验证失败补偿、积压和最终到账；目前不假定这些组件存在。

**3. 建议测试类型**

按“正确性检查 → 基线 → 负载 → 压力 → 突增 → 稳定性”执行。容量结论从压力测试中提取，注明环境配置和负载模型。

先通过低负载业务校验，再增加压力；发现积分或库存错误，立即停止升压并排查。

**4. 场景方案**

混合流量暂定：商品查询 **40%**、积分查询 **20%**、提交兑换 **30%**、兑换结果查询 **10%**，均为假设。另设纯兑换写入场景，避免读请求掩盖写入瓶颈。

| 场景 | 执行方式，数字均为假设 | 观察重点 |
|---|---|---|
| 基线 | 总到达率 5 请求/秒，持续 10 分钟 | 各交易耗时、业务正确性、初始资源消耗 |
| 常规负载 | 总到达率依次为 20、50、100 请求/秒，每档 15 分钟 | 成功吞吐是否随输入增长，尾延迟是否恶化 |
| 热点兑换 | 使用同一商品重复上述档位；库存设置为可耗尽 | 超卖、锁等待；售罄后是否快速、正确拒绝 |
| 重复提交 | 同一用户同一兑换意图并发提交 2、5、10 次，并覆盖超时重试 | 是否只产生一次有效兑换，扣账是否一致 |
| 压力／容量 | 从已稳定档位开始，每档增加 25%，保持 10 分钟 | 找出首次持续违反暂定阈值的区间，再缩小区间复测 |
| 突增／恢复 | 从稳定到达率升至 3 倍，保持 2 分钟，再回落观察 10 分钟 | 拒绝、超时、积压及恢复速度 |
| 稳定性 | 使用已验证稳定容量的 60%，持续 4 小时 | 内存、连接、延迟、积压是否持续增长 |

使用固定到达率模型，记录实际发出量、完成量和在途请求数；**请求/秒不等于并发用户数**。若压测机无法按计划发出请求，该档不能用于判断系统容量。

**5. 指标和退出标准**

暂定评审阈值，均为假设：

- 查询请求：P95 ≤ **500 ms**；提交兑换：P95 ≤ **1 s**、P99 ≤ **2 s**。
- 非预期技术失败率 ≤ **0.1%**。余额不足、售罄、限流等预期拒绝单独统计，不能全部算成错误，也不能当作兑换成功。
- 突增回落后 **5 分钟**内恢复到原稳定档位的延迟、吞吐和积压水平。
- 拟定业务红线：重复扣账、超卖、账实不一致均为 **0**，待业务确认；发现任一实例立即中止相关场景。
- 暂定中止条件：技术失败率超过 **5%**并持续 **1 分钟**，或资源耗尽、积压持续失控。预期的库存耗尽不属于系统故障。

监控至少包括：各交易实际吞吐、成功兑换量、P95/P99、超时、拒绝原因、CPU、内存、连接池、数据库慢查询和锁等待；存在缓存、队列时再补充对应指标。兑换请求被接收与兑换最终完成需分开计时。

结果报告应解释：瓶颈证据、首次失守档位、稳定容量区间、恢复表现及兑换对账结果。只能报告**本环境、本数据和本负载模型下**的结论，不能直接换算线上承载人数。

**6. 执行备注**

在隔离测试环境执行，使用测试积分、库存和账户。记录部署配置、数据库规模、索引、依赖配置以及冷／热缓存状态；替代外部依赖时明确其对结论的限制。

准备普通用户、余额不足用户、充足库存、临界库存和热门商品。账户及库存数量按“兑换到达率 × 时长”估算，避免正常容量测试提前耗尽数据。每轮保存初始账目，结束后核对积分流水、库存和兑换记录。

当前缺口：

- **业务规则**：扣积分和扣库存的原子性、幂等规则、失败回滚／补偿、兑换完成的定义。
- **需求目标**：可接受等待时间、错误率、预期峰值、活动规模、增长预期。
- **流量模型**：读写比例、热门商品集中度、重复点击和重试频率。
- **系统与环境**：部署规模、数据规模、数据库／缓存／队列、外部依赖、测试环境与线上差异。
- **执行条件**：实际接口和鉴权、测试数据准备方式、监控权限、环境资源限制。

优先补齐业务规则、环境和接口信息，即可开始低负载正确性检查与基线测试；正式容量验收仍需产品确认需求目标。
