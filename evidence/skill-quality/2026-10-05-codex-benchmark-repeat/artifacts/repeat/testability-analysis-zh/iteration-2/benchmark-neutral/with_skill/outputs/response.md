本评审针对“订单服务—消息队列—支付适配器—外部支付商”链路，目标是形成可执行、可复核的测试方案。**现有能力支持部分沙箱验证，但不足以证明异常恢复、端到端隔离和重复支付防护可靠。**以下仅为设计评审与验证计划；没有执行记录，不能声称改进有效或架构已通过验证。

**1. 输入审计与结论边界**

| 类型 | 内容 |
|---|---|
| 输入事实 | 订单服务通过消息队列调用支付适配器；适配器依赖外部支付商；沙箱有回调模拟器；没有故障注入入口；消息队列可配置隔离主题。 |
| 待核验判断 | 消息可能重复、延迟或乱序；支付请求超时后可能已完成扣款；回调可能重复或晚到。这些是需要覆盖的失败模型，并非已确认的系统行为。 |
| 关键缺口 | 架构图、消息与支付接口契约、回调接收方、结果返回路径、订单与支付状态机、存储边界、确认消息的时机、重试与死信策略、幂等机制、回调鉴权、部署配置及已有测试记录。 |
| 证据质量 | 当前只有文字架构描述，无版本、配置、代码或运行证据。可以识别风险并提出候选接缝，不能确认接缝已存在、隔离有效或失败恢复正确。 |

特别需要确认支付结果如何回到订单服务。回调由谁接收、接收后如何持久化与传播，直接决定测试断言和故障注入位置。

**2. 风险与优先级**

优先级依据业务影响和当前难以探测、复现的程度；缺少历史数据，不能判断实际发生概率。

| 优先级 | 风险与依据 | 处理顺序 |
|---|---|---|
| P1 | 请求超时、消息重投或回调重复可能引起重复支付、订单与支付状态不一致；潜在资金影响大。 | 先明确幂等、未知支付结果和状态迁移规则，再验证。 |
| P1 | 隔离主题只能证明具备一种隔离配置能力；消费者、数据库、回调及支付商账户仍可能互相干扰。 | 故障实验前验证完整隔离边界。 |
| P1 | 没有故障注入入口，关键异常难以稳定触发；无法可靠验证恢复策略。 | 增加受限的测试接缝与故障控制。 |
| P2 | 缺少关联证据、配置快照与自动化控制信息，失败原因可能无法定位或复现。 | 随上述工作同步补齐最低证据能力。 |
| P3 | 大规模并发、长时间运行、真实网络复杂故障。 | 基础正确性与隔离验证后扩展。 |

若后续发现真实重复扣款或测试流量进入生产，应升级为 P0；当前没有证据支持宣布存在这类事故。

**3. 组件、异步边界与测试接缝**

下面均为**候选设计，需由实际架构和实现核验**。

| 边界 | 需要验证的问题 | 接缝与替身策略 | 价值、成本与限制 |
|---|---|---|---|
| 订单服务→消息队列 | 若创建订单涉及持久化，订单写入与消息发布能否保持一致？发布失败如何恢复？ | 抽象发布接口用于组件测试；使用真实隔离主题验证发送、消费及确认语义。若存在双写缺口，再评估事务消息或 outbox。 | 可定位发布一致性问题；接口接缝成本低至中，一致性机制改造成本中至高。发布替身不能证明真实队列行为。 |
| 队列→支付适配器 | 消费失败、重投、重启与确认时机是否导致丢失或重复处理？ | 将业务处理与消费者生命周期分离；业务逻辑可独立测试，重投与确认必须用真实队列验证。 | 提高控制性；成本中。队列版本和配置会影响结果。 |
| 适配器→支付商 | 超时、拒绝、响应异常和“已受理但响应丢失”如何处理？ | 可替换支付客户端或测试环境出站地址；使用契约替身、受控代理触发异常，再以沙箱验证真实协议。 | 核心异常可稳定复现；成本中。替身不能证明支付商实际行为。 |
| 支付商回调→实际接收方 | 验签、重复、乱序、晚到，以及回调和同步响应竞争是否正确？ | 复用回调模拟器；核验其能否设置内容、投递次数、顺序及发送时间，并控制合法与非法签名。 | 复用成本可能较低，扩展成本待评估。模拟器存在不等于回调验证已充分。 |
| 状态持久化→订单最终结果 | 崩溃前后是否存在已扣款、未记账或结果未传播的窗口？ | 在隔离环境控制进程生命周期；必要时对具体持久化操作注入一次性失败。只读查询业务状态与处理记录。 | 可验证恢复闭环；成本中至高，具体取决于存储与事务边界。 |

不同层级使用不同替身：组件测试控制业务输入；真实队列测试异步投递语义；支付契约测试检查请求与响应结构；沙箱测试检查协议和鉴权。每层证据只支持该层结论。

**4. 通用维度与最小改进**

不用无证据的总分。当前定性评估为：**隔离、回调控制具备部分基础；故障注入缺少明确入口；其他维度证据不足。**

| 维度 | 最小执行项 | 成本与验收证据 |
|---|---|---|
| 可观察性 | 建议关联订单、支付尝试、消息、回调及测试运行标识；记录消费次数、状态迁移、重试原因、外部请求结果和时间。日志脱敏。 | 中；能够从一笔测试订单追溯完整因果链，并用持久化业务状态核对结果。日志本身不能证明没有重复扣款。 |
| 可控制性与故障注入 | 测试部署支持切换支付替身、暂停消费者、控制回调及按请求注入一次性异常；输出故障命中记录。 | 中；证据显示目标请求命中指定故障，其他请求未受影响。不得绕过业务鉴权或提供公共后门。 |
| 隔离 | 按测试运行隔离主题、消费组、数据命名空间、回调路由及支付标识；核验沙箱账户、额度和限流是否共享。清理仅按本次运行标识执行。 | 中；并行测试互不消费、互不修改数据，回调只到目标环境。共享支付商资源仍可能干扰。 |
| 确定性 | 组件测试使用可控时钟和固定随机种子；集成测试使用明确事件屏障、有限等待和完整事件记录，避免靠固定睡眠判断完成。 | 低至中；同一输入与故障计划可重复产生同一业务结果。真实网络时序仍有波动。 |
| 数据准备 | 创建独立订单、支付标识及脱敏账户；分别准备重复投递和新支付尝试的数据，避免混淆幂等范围。 | 低至中；记录数据清单与初始状态，清理范围可审计。 |
| 环境复现 | 固定代码、镜像、队列与存储版本，保存重试、确认、超时、回调和替身配置；敏感值仅记录安全引用。 | 中；另一执行者能依据环境清单重建实验，并记录与生产的差异。 |
| 自动化接口 | 核验模拟器是否已有脚本接口；补齐准备数据、投递事件、等待状态、查询证据及清理的入口。 | 低至中；流程可无人值守运行，失败返回明确原因并保留证据。 |

故障入口应只存在于专用测试部署或受限测试组件中，并具备最小权限、作用范围、次数限制和自动失效机制；部署检查应能证明生产无法启用。

**5. 可执行验证方案**

执行前先由订单、支付和业务负责人批准状态迁移、幂等范围、未知结果处理方式及等待上限。下表中的预期是**建议验收标准**，需落实为系统契约。

| 场景 | 前置条件与刺激 | 预期与所需证据 |
|---|---|---|
| 正常闭环 | 独立订单、隔离主题和合法回调；发起支付并观察至约定终态。 | 订单与支付状态一致；保存消息、支付请求、回调、状态迁移和沙箱交易记录。 |
| 消息重复与重启 | 明确幂等键和确认时机；重复投递同一支付指令，在处理与确认之间重启消费者。 | 不产生额外资金交易，状态不回退；保存投递次数、幂等处理记录及支付商交易记录。多次请求与多次扣款必须区分。 |
| 支付结果未知 | 替身先记录受理，再断开响应；随后发送合法成功回调。 | 不把通信超时直接当成支付失败；按批准的查询、等待或人工处理规则收敛。保存受理记录、超时、重试和最终状态。替身结果只能证明本地处理逻辑。 |
| 回调重复、乱序、晚到 | 接收方与签名规则已确认；模拟器重复发送同一回调，再发送冲突或过期事件。 | 重复事件不产生重复业务效果；冲突事件按批准规则处理；保存事件顺序、验签结果与迁移记录。 |
| 非法回调 | 构造错误签名、未知订单或不匹配金额的事件，走正常回调入口。 | 拒绝或隔离事件，业务状态不被错误修改；保存脱敏请求、校验结果及前后状态。 |
| 持久化失败与恢复 | 已识别关键写入位置；在支付结果写入前后分别终止进程或注入一次失败，再重启。 | 恢复后没有无法解释的资金与订单差异；保存故障命中、重投、存储及外部交易证据。 |
| 并行隔离 | 两套运行标识、主题、消费组、数据和回调路由；同时执行，一套注入故障。 | 另一套不消费其事件、不修改其数据、不接收其回调；保存路由、消费组及数据归属记录。 |
| 延迟与重试耗尽 | 明确重试、死信及恢复规则；暂停消费者或持续返回可重试错误，再恢复。 | 重试有界，失败可发现，恢复或人工接管路径可执行；保存次数、时间、死信及处置记录。 |

每次运行保存：环境与版本清单、初始数据、刺激计划、故障命中记录、带时间与关联标识的事件序列、断言结果，以及清理结果。判定“未重复扣款”需要支付商交易记录或可靠查询证据，不能只看适配器调用次数。

**6. 阻塞条件、人类决策与残余风险**

建议负责人分工：架构负责人确认链路与持久化边界；支付负责人定义幂等与未知结果处理；平台负责人验证隔离和部署限制；测试负责人组织实验并归档证据。

需要人类决策的事项包括：

- 超时后的重试、查询、等待及人工接管策略，尤其是支付商不保证幂等时。
- 冲突回调、订单关闭后支付成功等情况的业务处置与补偿规则。
- 可接受的处理时限、共享沙箱资源范围，以及接缝改造成本。
- 发布门槛与残余风险接受人。

未确认环境归属、数据隔离或故障作用范围前，停止故障实验；缺少状态契约、关键故障覆盖或资金侧证据时，不能据此批准支付正确性。发现串扰、异常交易或持续不一致时，停止刺激、保留证据并交由指定负责人处置。

第一步应补齐架构图、接口与状态契约、队列配置和模拟器能力说明，再执行一次正常闭环及一次重复消息实验，建立证据基线。后续增加“已受理但响应丢失”和崩溃恢复实验。

即使上述实验通过，仍存在沙箱与生产差异、替身契约漂移、支付商隐藏重试及真实并发时序风险；应记录差异，通过契约复核和进一步验证缓解，并由业务与技术负责人明确接受范围。
