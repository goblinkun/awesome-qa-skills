该架构有一定测试基础，但**尚不能判断它能稳定验证支付失败、重复消息和异步恢复**。隔离主题有助于隔离消息流量，回调模拟器有助于构造回调输入；两者的覆盖范围、控制能力和执行结果仍缺少证据。以下是待实施的改进与验证方案，本次未执行系统测试，不能声称方案有效。

**输入事实与待核验判断**

| 输入事实 | 可以得出的结论 | 仍需核验 |
|---|---|---|
| 订单服务通过消息队列调用支付适配器 | 存在异步消息边界 | 投递、确认、重投、排序、死信及消费并发配置 |
| 适配器依赖外部支付商 | 存在外部依赖边界 | 调用协议、超时、幂等、查单与错误分类能力 |
| 沙箱有回调模拟器 | 已有一种测试输入工具 | 是否支持签名、指定交易、重复、乱序、延迟及非法报文 |
| 没有故障注入入口 | 当前缺少明确的故障控制能力 | 代理、客户端配置或测试部署是否允许其他注入方式 |
| 消息队列可配置隔离主题 | 可以划分测试消息通道 | 消费者、重试与死信通道是否同样隔离 |

订单状态机、回调接收位置、支付结果回传路径、数据库和缓存结构均未提供，不能当作既有事实。

**组件、边界与测试接缝**

已知主链路是：`订单服务 → 消息队列 → 支付适配器 → 外部支付商`。回调模拟器进入哪个组件、如何最终更新订单，需要补全。

| 边界 | 建议接缝与替身 | 验证目标及限制 |
|---|---|---|
| 订单生成支付请求 | 将业务决策与消息发布接口分离；用记录型替身检查事件 | 验证金额、币种、订单标识、事件版本；不能证明消息实际送达 |
| 消息发布与消费 | 真实测试队列配合受控消费者、隔离主题 | 验证确认、重投、并发、重试和死信；内存队列难以代表这些语义 |
| 适配器调用支付商 | 提取支付客户端接口；提供可编程替身 | 构造成功、拒绝、超时、非法响应及“已受理但响应丢失” |
| 回调进入业务系统 | 使用现有模拟器；必要时补充报文注入工具 | 验证签名、去重、状态转换、乱序；其协议真实性仍需沙箱核验 |
| 异步结果落库 | 增加只读状态查询和处理记录 | 验证最终订单状态、支付记录和副作用一致性；实际存储结构待确认 |

支付客户端替身应保留请求历史，并能按同一幂等键返回先前结果。否则无法检查“重试是否导致重复扣款”。契约测试应约束报文、错误映射及签名规则；真实沙箱用于检查这些假设，不能用替身通过来证明支付商行为。

**改进优先级、成本与验证方式**

以下成本是相对估计，需查看代码和部署方式后才能确定。

| 优先级／成本 | 可执行改进 | 验证方式 |
|---|---|---|
| P0／低至中 | 绘制实际事件路径，记录状态转换、确认时机、重试和补偿规则 | 跟踪一笔沙箱订单，核对各跳记录与配置 |
| P0／中 | 为每次测试设置 `run_id`；隔离主题、消费者组、重试及死信通道 | 两次运行并行执行，检查消息和业务数据有无交叉 |
| P0／中 | 在支付客户端边界加入测试替身，支持超时和受理后响应丢失 | 检查请求历史、幂等键、恢复行为及最终状态 |
| P0／中 | 建立关联记录：订单、事件、支付尝试、幂等键、支付商交易号 | 从订单追踪到消息、调用和回调；敏感字段脱敏 |
| P1／中至高 | 在测试部署增加受控故障配置或网络代理 | 定向注入连接失败、响应延迟与中断，并记录命中请求 |
| P1／中 | 将时钟、重试间隔和随机退避参数设为可控依赖 | 用虚拟时钟验证逻辑；用真实队列单独验证实际调度 |
| P1／中 | 固化运行清单、种子数据和清理流程 | 按同一清单重建环境、重跑关键场景 |
| P2／高 | 逐步覆盖实例崩溃、持续积压和恢复容量 | 在隔离环境测恢复时间、重复处理和资源影响 |

隔离主题只解决部分隔离问题。还应检查数据库、缓存、沙箱商户、回调地址、限流额度及后台补偿任务是否共享。暂时无法隔离的共享资源应串行使用，并在报告中保留限制。

故障注入入口应限定在测试部署，通过独立配置启用；本方案不涉及生产写入。

**可观察性、可控制性与确定性**

- **可观察性：**记录消息发布、接收、确认、重投，支付调用起止与结果，回调验签与去重，以及状态转换前后值。单条成功日志不足以证明业务完成；需交叉核对状态、调用历史和处理记录。
- **可控制性：**支持暂停或启动测试消费者、选择故障命中的支付尝试、发送指定回调，以及重启测试实例。先核验现有模拟器能力，再决定是否扩展。
- **确定性：**固定输入、随机种子和故障触发点；通过事件或状态条件等待完成，设置有界超时，避免固定睡眠。将真实网络和队列时序作为单独的集成验证。
- **环境复现：**保存代码与镜像版本、消息队列版本及配置、数据库迁移版本、脱敏配置、数据种子、替身脚本、模拟器版本和执行命令。密钥通过引用注入，不能进入复现包。

真实异步系统很难保证完全相同的执行顺序。测试应验证允许顺序下的业务不变量，而不是依赖某次运行的日志顺序。

**可执行验证计划**

先由订单、支付负责人确认业务预期，再按以下场景执行。表中断言是建议验收目标，尚未证明当前实现满足。

| 场景与触发方式 | 建议断言 | 必须保存的证据 |
|---|---|---|
| 正常支付并发送成功回调 | 订单在约定期限内进入正确终态 | 消息、调用、回调及状态记录 |
| 对同一支付事件重复投递；重复发送回调 | 有效支付副作用不重复，状态不被错误覆盖 | 投递次数、幂等键、替身受理记录、状态转换 |
| 替身先记录受理，再返回超时 | 重试或查单能恢复，且不产生第二次有效支付 | 受理记录、后续调用与最终状态 |
| 延迟回调、先发新状态再发旧状态 | 按约定状态机处理；旧事件不造成非法回退 | 回调序列及接受／拒绝原因 |
| 在持久化与消息确认之间终止消费者，再重启 | 重投能恢复，副作用保持幂等 | 终止位置、重投记录及存储状态 |
| 发送非法消息或非法签名回调 | 不发生无界重试或未经验证的状态更新 | 重试／死信记录、验签结果、状态快照 |
| 暂停消费造成积压后恢复 | 达到约定恢复目标，未处理项可追踪 | 积压、吞吐、延迟及未决订单清单 |
| 两组测试同时运行 | 数据、回调和消息互不串扰 | 两组关联记录与隔离检查结果 |

执行顺序建议为：组件测试与契约检查 → 真实队列集成 → 沙箱回调核验 → 隔离环境故障与恢复测试。每个场景保存输入、版本、配置、故障命中记录、断言结果及失败原因。重复运行次数、最长等待时间和恢复目标应事先约定；不能用临时增加等待时间来掩盖失败。

**人类决策、证据缺口与残余风险**

需要业务和支付负责人决定：支付长时间未决时如何处理、允许哪些状态转换、退款和补偿政策、幂等键生命周期，以及可接受的恢复时间。实施人员可自行决定具体接缝和测试工具，但这些业务选择不应由测试方案代替。

当前缺少代码、队列配置、支付商契约、模拟器能力说明、状态机、运行日志和测试报告。取得这些证据后，才能确定哪些改进必需、哪些已有实现可复用，以及最终验收是否通过。

即使上述测试全部通过，仍有替身与真实支付商不一致、沙箱与生产行为不同、共享额度干扰、低概率竞态及容量差异等残余风险。通过结果只能支持**已执行场景和对应环境**，不能直接证明真实支付全链路可靠。
